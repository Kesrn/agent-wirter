## 1. 项目定位与改造主线

本项目是面向小说和长文创作者的 AI 创作平台。它的目标不是单次生成一段文字，而是将项目资料、章节写作、审校、人工确认、版本审计与长期记忆组织成可追溯的创作闭环。

改造主线可以概括为：

```text
基础创作工作台
  -> 项目资料库与章节上下文
  -> 可检索、可修正的结构化知识
  -> 可观测、可恢复的 AI Harness
  -> 职责明确的 Expert System v2
  -> 面向长篇的计划模式、节奏与角色弧
```

### 1.1 已确立的设计原则

1. 数据库是正式事实源；Skill 和 prompt 只能定义行为，不能另建私有记忆。
2. AI 草稿、抽取事实与用户确认后的设定必须分层保存。
3. 关键章节生成要先规划、再写作、再审校，最终由用户决定是否采纳。
4. 生成过程要有 Run、Step、LLM 调用和版本审计，失败时应可定位、可重试、可恢复。
5. 长篇能力的核心是连续性和可控性，不是无止境增加 Agent 或澄清问题。

## 2. 当前目标闭环

### 2.1 已实现主链路（实施总结记录）

```text
项目资料 / 知识库 / 已确认记忆
  -> Context Builder
  -> 澄清规划（按需）
  -> 章节策划师（ChapterTaskCard）
  -> 正文写手
  -> 结构审稿人
  -> 专业编辑
  -> 一致性审校
  -> 最终人工审核
  -> 保存章节版本与生成记录
  -> 剧情记录员
  -> 记忆管理员
  -> WritingMemoryStaging
  -> 用户确认后写入正式资料 / 下次生成上下文
```

### 2.2 计划模式当前状态与下一步收敛

截至 2026-07-12，生成前任务卡审核（L-1）和嵌入式澄清（L-2）已经在当前工作区实现并通过针对性回归：作者可查看和编辑 `ChapterTaskCard`、添加补充要求、回答最多三个澄清问题，并在同一面板内触发 Architect 重新规划。Writer 只有在作者确认当前任务卡后才会启动。

旧的独立 `ClarificationPanel` 与 `human_clarification` 恢复路径仍保留用于历史 Run 兼容；新 Run 默认只使用任务卡这一个生成前暂停点。该改动仍需随当前工作区一起提交，并使用真实模型完成端到端验收。

```text
用户发起章节生成
  -> AI 生成可见、可编辑的任务卡
  -> 在任务卡内补充可选澄清与作者要求
  -> 用户确认后生成正文
  -> 审校、确认、记忆治理
```

“计划可见优先于多轮追问”的第一版闭环已经完成。L-3 上下文预览和逐项排除也已接入任务卡；下一优先级是真实模型验收和持久化恢复。

### 3.1 2026-06-17：从“写作工具”走向“资料库 + 章节工作台”

起点是把创作项目拆成四层：正文、章节记忆、项目知识库和 AI 创作层。

关键决定：

- 每个小说项目拥有独立资料库，支持原文、设定、角色、时间线和规则。
- 章节生成不再只依赖当前输入，而是读取当前章节资料包和项目知识。
- 资料问答与章节助手是创作工作台的一部分，而不是独立聊天功能。

早期方案的有效结论已收敛到本文和当前权威设计文档；原始归档稿不再单独维护。

### 3.2 2026-06-18 至 2026-06-22：知识抽取质量与结构化事实治理

这一阶段识别出长篇资料抽取的真实难点：相似检索无法保证召回完整，LLM 也会将同一段里的人物和能力错误绑定。因此开始建设规则事实索引、结构化知识人工修正、别名归一与出场记录。

关键决定：

- 明确的“人物 - 能力”等事实在索引阶段沉淀，QA 优先查询事实而非让模型再次猜测。
- 人物档案维护稳定身份和状态；每章出现、提及和事件进入单独的章节记录，避免人物档案无限膨胀。
- 先保证知识质量与人工纠错闭环，不在此阶段过早引入 GraphRAG、重排序或更多向量基础设施。

早期抽取治理方案的有效结论已收敛到本文；后续以当前的知识库、结构化知识和 Harness 实现为准。

### 3.3 2026-07-01 至 2026-07-03：AI Harness A-H

Harness 的目的是让生成任务从“黑盒请求”升级为可追踪、可审批、可审计的执行过程。

#### A. 核心数据层

新增并关联以下核心实体：

- `AiRun`：一次 AI 工作流运行。
- `AiRunStep`：运行内每个节点的状态、输入和输出摘要。
- `LlmCallLog`：不可变的模型调用审计记录。
- `HumanInterrupt`：等待用户决定的审核或澄清节点。
- `GenerationRecord` 与 `ChapterVersion`：与 Run、接受版本和回滚关系关联。

#### B-D. 生成链路、调用审计与查询能力

- 完整生成创建 Run，并记录执行步骤。
- writer、critic、一致性检查等调用记录 prompt/context 快照与模型调用日志。
- 前端通过 SSE 收到 run 创建、步骤状态、专家输出和完成/错误事件。
- 提供项目级 Run 列表与单次 Run/Step 查询。

#### E-G. Human Review、版本审计与 Guardrail

- 人工审核状态持久化，重复批准具备幂等性。
- 批准正文后保存可追溯版本；回滚通过新版本实现，不覆盖历史。
- 一致性检查输出结构化 Guardrail 结果，高严重度问题可作为阻断提示。

#### H. Writing Memory Staging

- 批准后的章节可异步抽取人物、世界规则、事件、伏笔和剧情事实。
- 抽取结果先进入 staging，用户确认后才写入正式表或作为确认事实参与下次上下文构建。
- 未确认的 AI 信息不应污染正式设定。

### 3.4 2026-07-03 至 2026-07-06：Expert System v2 与 Workflow v2

旧系统中“创意大师、残酷大师、情节转折大师”等泛化角色被逐步替换为职责边界更清晰的专家。

| 专家 | 职责 |
| --- | --- |
| `chapter-architect` | 生成章节任务卡，只规划不写正文。 |
| `chapter-writer` | 依据确认的任务卡写正文。 |
| `structural-critic` | 检查结构、节奏、人物和同人风险，输出修改指令。 |
| `narrative-editor` | 根据审稿意见输出可用修订稿。 |
| `continuity-checker` | 校验人物、能力、时间线、原著事实与状态冲突。 |
| `story-recorder` | 从确认后的正文提取已发生剧情与状态变化。 |
| `memory-curator` | 决定哪些候选记忆适合进入 staging。 |
| `canon-researcher` / `scene-enhancer` | 按需调用的原著考据与局部场景增强。 |

同时，调度层采用确定性的工作流定义，而不是让 LLM 自由决定任意调用链，避免成本失控和不可测试的循环。

标准链路：

```text
context_loader
  -> chapter_architect
  -> chapter_writer
  -> structural_critic
  -> narrative_editor
  -> continuity_checker
  -> human_review
```

### 3.6 2026-07-07：可靠性修复与长篇能力 K-4/K-5

#### 可靠性

本轮专项文档记录了两类关键问题：

- Workflow 节点缺少异常捕获时，模型调用失败可能让前端永久停留在“进行中”。

已提出并记录的修复方向包括统一异常处理、120 秒调用超时、明确的前端错误反馈，以及后续的重试/取消能力。

## 5. 当前架构边界

```text
Vue / Electron 前端
  -> REST + SSE
FastAPI API
  -> 项目、写作、知识库、专家、评测、鉴权
Services / Harness
  -> 工作流定义、上下文构建、版本、记忆、检索、评测
LangGraph Workflow v2
  -> 规划、写作、审稿、编辑、一致性、人工中断
SQLAlchemy + PostgreSQL / SQLite
  -> 正式项目数据、Run 审计、版本、staging 与结构化知识
LLM / Embedding Provider
  -> OpenAI 兼容模型调用、资料抽取与检索向量
```

### 5.1 必须坚持的边界

- 正式设定只能来自用户录入或用户确认后的 staging，不应直接相信任何未审核模型输出。
- 长篇生成的目标上下文来自数据库、资料库与确认记忆，不能依赖 Skill 文件维护状态。
- 快速任务与严格任务必须使用不同工作流，避免所有操作都承担完整多 Agent 成本。
- API 路由、SSE 封装与业务编排应逐步拆分，避免单一 `routes.py` 持续膨胀。

## 6. 当前已知风险与待验证项

| 风险或缺口 | 影响 | 建议动作 |
| --- | --- | --- |
| L-2 尚未真实模型验收 | 自动测试已覆盖任务卡回环，但真实模型输出、长连接和重启恢复尚未完整验证。 | 提交当前改动后，以有效模型配置覆盖回答后重规划、直接确认、取消和超时场景。 |
| 完整多 Agent 链路成本高 | 日常续写可能慢且昂贵。 | 明确快速、标准、严格三档工作流，并显示调用成本/耗时。 |
| LLM 失败、超时与中断 | 用户可能看到长期“进行中”或丢失等待审核状态。 | 统一超时、重试、取消、恢复与状态持久化；对服务重启做恢复演练。 |
| SQLite 与 PostgreSQL 差异 | 桌面端、测试与服务端行为可能不完全一致。 | 为迁移、异步任务和检索能力建立跨数据库验收矩阵。 |
| 内存 checkpoint | 服务重启后等待审核的图状态可能丢失。 | 推进数据库 checkpointer 或使用持久化可恢复状态。 |
| 记忆 staging 审核负担 | 用户可能不愿逐项确认 AI 提取信息。 | 提供批量确认、置信度筛选、冲突合并和低风险自动建议，但保留作者最终决定权。 |
| 文章模式与小说模式复用过深 | 领域模型和 UI 可能出现语义别扭。 | 保留公共底座，逐步拆分两类内容的工作流、上下文与评测。 |

## 7. 推荐后续路线

### P0：计划模式与核心写作体验

1. 提交并用真实模型验收 L-1/L-2：回答后重新规划、直接确认、取消、超时和重复提交。
2. 在任务卡中展示本次模式（快速、计划、严格）与相应的等待/调用预期。
3. 推进持久化 checkpoint，保证服务重启后仍能恢复任务卡审核。
4. 增加服务端 Run 取消和节点级重试，避免只中断前端 SSE。

### P1：长篇叙事控制

1. 完成 K-4 节奏字段、接口和编辑 UI 的验收。
2. 完成 K-5 角色弧聚合视图，并加入章节范围过滤。
3. 将 Story Arc 扩展为卷、幕、弧等中层结构。
4. 补充伏笔生命周期：计划、埋设、活跃、揭示、回收、废弃。

### P1：可靠性与成本控制

1. 每个工作流节点统一配置超时、重试、可观测错误和幂等键。
2. 支持取消任务、从失败节点恢复和服务重启后的审核恢复。
3. 对上下文、任务卡和检索结果做缓存，减少重复调用和 token 消耗。
4. 将生成任务分为快速、标准、严格三档，避免轻量任务强制经过完整专家链。

### P2：工程与评测治理

1. 按项目、生成、知识库、Harness、评测等领域拆分 API 路由。
2. 用 Evaluation Lab 建立一致性、角色状态、伏笔回收、续写衔接等固定回归集。
3. 在真实 PostgreSQL 与桌面 SQLite 上分别验证迁移、检索、后台任务和恢复能力。
4. 持续清理已废弃专家与旧工作流的兼容边界，减少双链路维护成本。

### 8.1 文档分层

| 类型 | 位置 | 使用方式 |
| --- | --- | --- |

| 历史背景 | 本文第 3 节 | 已完成的早期方案和一次性执行清单的有效结论已收敛于此，不再保留重复文档。 |

### 8.2 更新本文件的规则

1. 每完成一个可独立验收的阶段，在第 3 节增加时间线条目，并把第 4 节状态从“计划”更新为“已具备”。
2. 每新增权威计划或实施总结，在第 8 节补充来源，同时说明它取代或依赖哪些旧文档。
3. 不把“设计完成”“代码存在”“测试通过”“真实用户验证”混为同一状态；必要时分别标注。
4. 专项故障修复要在第 6 节关闭或保留风险说明，避免同一问题在后续规划中被重复忽略。

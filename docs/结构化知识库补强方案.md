## 3. P-1 章节编号修复（新增，最高优先级）

### 3.1 现状证据（真实库核查）

| 事实 | 原文 | 切分表现状 |
|---|---|---|
| 全文最后标题 | 第 3233 章 | chapters 表 3130 行（旧切分）；新解析 **3132 个标题**，末行 ordinal=3132（"人间，惹不起了"） |
| 铁笼章节 | 第 613 章（标题"肉丘障碍"，含铁笼内容） | 铁笼内容被记成 **chapter_no=617** |
| 梵葵陷阱（穆白） | 第 3195 章 | 被记成 **chapter_no=3092** |

根因：
1. 切分把 `chapter_no` 写成**循环序号 1,2,3…**，未保存标题里的原始章节号；
2. 中间既有多切也有漏切（**3132 个可解析标题 vs 末章号 3233**，含作者跳号 957~966、格式恢复 1313 等变体），**不能用固定偏移修正**；
3. `chapter_title` 只存标题文本（"世界大变"），**"第1章"等原始标签未保存**——切分表无法自我校正，必须回到原始 txt 重新解析。

### 3.2 修复方案

重新切分 + 双编号，**先新代 dry-run，验收通过后切换，不原地删除旧切分**（旧 `project_source_chapters` 仍被 staging、出场、事件记录引用，直接删除会产出孤儿 `chapter_id`）。

```
project_source_chapters 增加列：
  source_ordinal        INT    -- 数据库内顺序 1..N（任务推进/排序/断点续跑用）
  display_chapter_no    INT    -- 原文标题中的 613 / 3195 / 3233（解析失败可空）
  original_label        TEXT   -- 原始章节标签原文（"第613章 肉丘障碍"）
  chapter_title         TEXT   -- 仅标题文本（"肉丘障碍"）
  start_offset          INT    -- 该章在 source 原文中的起始偏移（字符）
  end_offset            INT    -- 该章在 source 原文中的结束偏移
  content_hash          TEXT   -- 该章正文哈希（验证重切无丢字/重叠/串章）
  source_content_hash   TEXT   -- 来源全文哈希（该代切分基于的原文版本）
  split_generation_id   UUID   -- 切分代次
  parse_warning         TEXT   -- 检测到的问题（重复/缺号/乱序/无法解析）
```

**旧 `chapter_no` 语义（兼容策略）**：
- `source_ordinal`：任务推进、排序、断点续跑使用；
- `display_chapter_no`：用户引用和展示使用；
- 旧 `chapter_no` 暂时等于 `source_ordinal` 保持兼容，后续逐步废弃；
- 非数字章节（番外/楔子）、重复章号依赖 `original_label`，**不强行生成数字章号**；
- 抽取任务的 `chapter_no_start/end` 过滤条件必须明确按 `source_ordinal`（推进）还是 `display_chapter_no`（展示）——默认按 source_ordinal。

**标题解析器要求**：
- 同时支持阿拉伯数字（"第613章"）、中文数字（"第一章"，行首实为 3 处，全文任意位置粗探测 79 处仅供参考）、带空格/全角空格变体；"楔子/序章/番外"等非数字标题单独分类；
- 保留 original_label；`unparsed_heading_count` 为**真实扫描**（`scan_unparsed_headings`：行首"第"+章节词但无法解析的行），实测 3 个候选已全部决议："第956~967章 三方聚头"（**作者跳号**：正文连续，恢复 display=967，957~966 标记 `author_numbering_skip`，共 10 个编号）、"第1313亮晶晶章 大雷爆"（**格式恢复**：display=1313）、正文句子 1 条（固化 `false_positive_body_text`）；
- 顺序校验：重复章号、缺号、乱序（display 与 ordinal 方向不一致）、区间重叠/丢失（相邻章 start/end 连续性 + 全文首尾覆盖）。

**收录完整性语义（区分"收录至"与"完整覆盖"）**：
- `corpus_end_chapter = 3233`：资料**最晚收录至**第 3233 章；
- `corpus_complete = false/unknown`：**不能确认** 1~3233 章完整。dry-run 实测：**3132** 个标题（阿拉伯 3127 + 中文数字行首 3 + 恢复 2）、末章号 3233、缺号 122 个（含作者跳号 957~966 已剔除 10 个、格式恢复 1313 已剔除 1 个）、重复章号 31 处、逆序 5 处——缺号可能确为缺失，也可能是格式变体（见 §3.3 决议模型）；
- `chapter_gap_manifest`：缺号清单（JSON）；
- 问答表述纪律："资料最晚收录至第 3233 章，检测到若干章号缺口"——**不得暗示完整无缺**。

**切分验收（P-1 第二阶段，全部通过才允许 LLM 抽取）**：
1. 铁笼内容 → display_chapter_no == 613；梵葵陷阱 → 3195；最后标题 → 3233；
2. 章节内容区间无重叠、无丢失（start/end 连续性 + 哈希校验）；
3. display 章号总体单调，重复与逆序全部报告；
4. 随机抽查开头、中段、结尾各 10 章的正文完整性；
5. 验收 CSV 列名明确：`source_ordinal / display_chapter_no / original_label / title / start_offset / end_offset / content_hash / warning`——**不使用含义不明的 `chapter_no` 列名**。

### 3.3 异常分类与解析器收紧（P-1 阶段二，dry-run 实测）

真实语料含大量**伪标题**，必须自动分类、人工只审可疑项：

| 类别 | 含义 | dry-run 实测 | 建议处理 |
|---|---|---|---|
| `false_heading` | 作者更新说明（"第一章：中午12点"）、手打水印尾巴（"…是由【无*错】【小-说-网】会员手打"）、站点广告（"最快更新，无弹窗"） | 9 | **drop_entire_span**：整段排除，不并入前章 |
| `page_artifact` | 翻页残片（"第2074章 魔宰 (第1/1页)"）、空章节（标题后无正文） | 10 | **drop_entire_span**：整段排除，不并入前章 |
| `duplicate_label` | 同一 display 章号多次出现（1416/1417 同是"第1426章"） | 决策后剩 **8 组 keep_duplicate**（725/779/1124/1518/1805/2522/2586/2776） | 完整不同正文必须保留，保留重复展示号由 `source_ordinal` 保证唯一；7 项改号见 renumber_candidates |
| `suspected_misnumber` | 章号回跳（1862→1683、2155→2066）——原文错标或拼接污染，**不能统一解释为多卷重号** | 5 | 人工确认后修正 display 号 |
| `source_gap` | 缺号连续段——真实语料缺口候选（957~966 为作者跳号已剔除、1313 已格式恢复） | 20 段 / 122 章（决策后 16 段 / 115 章） | 按缺号决议模型归类（§3.5），缺章人工确认 |
| `manual_review` | 正文过短（<100 字）且无明确模式 | 0（已全部归入上两类；若再出现则人工核对） | 人工核对是否残片/错切 |

实现（已落地 `services/chapter_parser.py` + `scripts/chapter_dryrun.py`）：
- 伪标题过滤：翻页模式（`(第1/1页)`）、更新说明（短标题+时间词/更新标记）、水印（"会员手打/是由/请到"）、正文过短（<100 字）；
- 完整 SHA-256（64 hex）+ `source_content_hash` 全文哈希；解析器单测 16 用例全过（`tests/test_chapter_parser.py`）；
- 异常复核清单 CSV：每项含前后章节、内容长度、首尾片段、建议处理——**人工只审 `manual_review` 与抽查已分类项，不逐项看原始清单**；
- dry-run 只读连接（`mode=ro`），地标验收在重复章号时列出全部候选并标注，验收状态分级：**"地标通过 ≠ 验收通过，异常未清零不得进入写库阶段"**。

### 3.4 异常决策账本（P-1 阶段三，人工裁决输入）

`scripts/chapter_decision_ledger.py` 产出清单（已归档 `tmp/chapter_dryrun/`），**最终决策统计（全部 3132 章）**：

```
keep 3101 / drop 16 / renumber 7 / keep_duplicate 8
应用后：保留 3116 章、回跳 0、重复 8 组、剩余缺号 115 章 / 16 段
```

1. **anomaly_review.csv（59 个独立 ordinal）**：按 ordinal 去重聚合（一个 ordinal 多分类合并为主+次分类，修正"105 项"的重复计数口径）；每项带 `auto_decision`（keep/drop/renumber/keep_duplicate/unresolved）与人工 `decision` 列；
2. **renumber_candidates.csv（15 项）**：
   - **7 项 renumber（高置信，目标均填补缺号）**：ord 463→459、1858-1861→1863-1866、2151→2156、2394→2400；
   - **8 项 keep_duplicate**：ord 728/782/1117/1512/1800/2517/2582/2772——目标号已被保留章节占用，保留重复展示号（`source_ordinal` 保证唯一）；
   - 占用集合**随改号逐步更新**（effective 映射）：ord 2394 改 2400 后，ord 2395 自动恢复 keep 2401，不再误判 keep_duplicate；
3. **gap_review.csv（两组）**：`original` 20 段/122 章；`projected`（应用 renumber 后）**16 段/115 章**——459/1863-1866/2156/2400 已填补，其余缺口标记 `accepted_missing_in_supplied_source`（不阻塞写库，保持 `corpus_complete=false`）。

**drop 语义（drop_entire_span）**：16 项 drop 为作者说明/广告/翻页/水印噪音，**整段排除，不并入前一章**；阶段四将偏移与哈希记入排除清单，全文完整性验收满足：

```

```

**最终映射不变量测试**（`tests/test_chapter_parser.py` 20 项 + `tests/test_chapter_ledger.py` 11 项，合计 31 项全过；知识库回归 115 项，总计 146）：应用全部决策后无回跳、重复组数 = keep_duplicate 组数、renumber 目标不在 projected 缺号中。

人工裁决确认（keep_duplicate 8 组接受保留重复号、renumber 7 项照准、gap 16 段标记 accepted_missing）后进入 P-1 写库阶段。

> ⚠️ 在 P-1 完成前，**不得**启动任何 LLM 抽取——错误章号会污染全部引用。

### 3.5 切分代次与切换（P-1 阶段四设计）

与抽取 generation 同思路独立实现：切分是可重建的派生数据，但章节 id 被出场/事件记录引用，必须代际管理、原子切换。

```sql
-- 切分代次
split_generations:
  id UUID PK
  project_id, source_id
  source_content_hash TEXT    -- 切分基于的原文哈希（激活前必须与当前原文一致）
  parser_version TEXT         -- 解析器版本（chapter_parser 模块版本）
  decisions_hash TEXT         -- 决策账本哈希（按 ordinal 排序的规范化最终决议 JSON 的 SHA-256，不直接哈希 CSV）
  decision_ledger JSON        -- 决策明细快照（16 drop / 7 renumber / 8 keep_duplicate / 恢复与跳号决议）
  status                     -- building / validating / ready / active / failed / superseded / legacy
  validation_report JSON     -- 验收报告（地标/区间/不变量/landmark_checks/verdict/unparsed_resolution）
  created_at, activated_at

-- 活动切分代指针（每 source 一行）
source_split_state:
  project_id, source_id       -- 联合主键
  active_split_generation_id FK

-- 章节行（新代写入此表，旧代不删除）
project_source_chapters:
  ... 现有列 ...
  split_generation_id UUID NOT NULL   -- 新增
  source_ordinal INT NOT NULL         -- 新增（代内唯一）
  display_chapter_no INT NULL         -- 新增（允许重复：8 组 keep_duplicate）
  original_label TEXT                 -- 新增（原始标题标签）
  start_offset INT, end_offset INT    -- 新增（原文定位）
  content_hash TEXT                   -- 新增（完整 SHA-256）
  UNIQUE(split_generation_id, source_ordinal)   -- 唯一键（display 可重复）
  -- 旧 chapter_no 保留兼容（= source_ordinal），逐步废弃

-- 排除噪音区间（16 段 drop + 首部 41 字符）
split_exclusions:
  split_generation_id FK
  kind                      -- noise / preface
  start_offset INT, end_offset INT
  content_hash TEXT
  reason TEXT               -- false_heading/page_artifact/watermark/preface
  ordinal_ref INT NULL      -- drop 的章节 ordinal（noise 时）
```

**切换与引用规则**：
1. 新代在 `split_generations(building)` 下**完整构建**（含 exclusions 与验收报告）；
2. 验收通过（地标 613/3195/3233、区间无重叠丢失、不变量、决策哈希一致）→ `ready`；
3. **单事务 + 并发保护（CAS 带 base）**切换 `source_split_state.active_split_generation_id`：切换必须**比较旧活动代**——
   ```sql
   UPDATE source_split_state
   SET active_split_generation_id = :new_generation
   WHERE project_id = :pid AND source_id = :sid
     AND active_split_generation_id = :base_active_split_generation_id  -- 必须传旧代，不能只用 IS NULL
   ```
   条件更新影响行数 = 1 才算切换成功（两个 ready 代并发时只有先到者生效，后者重试）；失败/中断 → 保持 `building/failed`，读取继续走旧代；
4. **抽取任务固定引用 `split_generation_id`**：任务启动时锁定该代，运行中不随活动指针漂移（抽取基于的章节定义中途不得变化）；
5. 旧章节行**不删除**，至少保留上一代支持回滚；
6. **全文完整性验收**：`保留章节区间 + 排除噪音区间 + 首部 41 字符 = 原始全文`（偏移/哈希逐段比对）；
7. **所有章节读取路径统一按活动代（或任务固定代）过滤**：集中到 repository/service，禁止各 SQL 自行拼接。

**缺号决议模型**（gap 的每一段必须归入且仅归入一类）：

| 决议 | 含义 | 现状（决策后） |
|---|---|---|
| `author_numbering_skip` | 作者编号跳跃（"第956~967章"：正文连续，作者把 956 的下一章误编号成 967） | **10 章**（957~966，1 段）——已从缺号中剔除，display 记 967 |
| `format_recovered` | 格式异常已恢复（"第1313亮晶晶章"→1313） | 1 章——已恢复 |
| `source_missing` | 源文件确实缺失 | 待核对（unparsed 扫描 + 人工） |
| `accepted_missing_in_supplied_source` | 接受缺失，不阻塞写库（保持 `corpus_complete=false`） | 决策后 **115 章 / 16 段** |

**旧数据迁移方案（写库实现顺序）**：不能直接给现有章节加 `split_generation_id NOT NULL`——
1. 建 legacy generation（`split_generations(status='legacy', source_content_hash=当前原文哈希, parser_version='legacy', decisions_hash=NULL)`）——legacy 是迁移占位代，状态枚举含 `legacy`，不参与 active 切换竞态；
2. 现有章节回填 `split_generation_id=legacy` + `source_ordinal=旧 chapter_no` + `display_chapter_no=NULL`（旧数据无可靠章号，标记待重切）；
3. 切换活动指针 → legacy；
4. 全部读取路径按活动代过滤验证通过后，**再收紧 `NOT NULL` 约束**；
5. 新代构建完成并验收后，单事务 CAS 切换指针到新代（legacy 保留供回滚，标 `superseded` 或保持 `legacy`）。

**迁移验收（写库前必须通过）**：新代构建后，抽样核对——铁笼 → display 613、梵葵陷阱 → 3195、末章 → 3233；16 段 projected gap 全部标记决议类别（author_numbering_skip 10 章已剔除；115 章标记 `accepted_missing_in_supplied_source`）；8 组 keep_duplicate 以 `source_ordinal` 唯一。

## 4. P0 抽取代际原子切换（设计定稿）

### 4.1 问题

现有抽取流程每完成一章立即合并进正式表：中断后前段新数据已生效、后段旧数据仍在，半新半旧混用，无法回滚。

### 4.2 独立表设计（不复用 retrieval_index_generation）

检索索引是可删除投影，结构化知识是业务事实——生命周期、保留、人工覆盖规则都不同。**复用设计思想，独立建表**：

```sql
-- 抽取代次（一个 source 一次全量/增量抽取 = 一个 generation）
extraction_generations:
  id UUID PK
  project_id, source_id
  canon_level        -- original / fanfic（代际按层级隔离）
  origin             -- llm_extracted / rule_extracted
  source_content_hash TEXT   -- 抽取基于的原文哈希（激活前必须与当前原文一致）
  split_generation_id UUID   -- 所基于的切分代次
  schema_version     TEXT     -- 抽取输出 JSON schema 版本
  prompt_version     TEXT     -- 抽取 prompt 版本
  model, provider    TEXT     -- 模型与供应商
  target_chapters INT, completed_chapters INT, failed_chapters INT
  validation_report JSON     -- 覆盖率/失败率/别名命中/evidence 校验报告
  status             -- running / validating / ready / active / failed / abandoned / superseded
  created_at, activated_at, abandoned_at

-- 每个 source 每层的活动指针（隔离键）
extraction_source_state:
  project_id, source_id, canon_level, origin  -- 联合主键
  active_generation_id FK
  -- 保证原著/同人/人工设定互不覆盖

-- 章节级抽取进度（续跑/诊断）
extraction_chapter_state:
  generation_id, source_ordinal, display_chapter_no
  status             -- pending / ok / failed / accepted_failed
  raw_output TEXT    -- 失败时保留 raw LLM 输出（原文，避免 JSON 解析失败丢数据）
  raw_json JSON NULL -- raw_output 可成功解析时的结构化副本（可空）
  validation_error TEXT
```

### 4.2.1 主档快照回滚（character_profile / character_relations）

主档虽是"跨代合并"（不按代隔离），但**必须支持回滚到上一代**，否则切换后发现新代质量差时无法恢复：

- `character_profile` / `character_relations` 行增加 `updated_in_generation_id UUID`（最后写入代）；
- 切换时**同事务**生成主档快照行（或快照表 `extraction_master_snapshot`：generation_id + 序列化主档子集）；
- 回滚 = 用上一代快照整体恢复主档（含 manual 覆盖关系，快照保存的是"生效视图"而非原始行）；
- 快照保留至少一代；人工修改（manual）在快照中标记，回滚时不覆盖 manual 字段。

### 4.3 稳定主档 vs 代际事实表（唯一约束迁移矩阵）

| 表 | 角色 | 唯一约束现状 | 迁移方案 |
|---|---|---|---|
| character_profile | **稳定主档**（人物身份跨代累积，代际合并更新） | project_id + name | 维持不变；新代写入用 upsert（按 name 合并，字段级覆盖按 canon_level/origin 优先级）；加 `updated_in_generation_id` 支持快照回滚 |
| character_relations | 稳定主档 | （无唯一约束，按 id 关联） | 维持；增加 chapter_no/evidence/confidence/origin 后按"source+target+chapter"去重；加 `updated_in_generation_id` |
| character_alias_clusters | 稳定主档（人工确认） | project_id + canonical_name | 维持；LLM 候选只建议，入表必须人工确认 |
| ability_profile | **代际事实表** | project_id + character_name + ability_type + ability_name | 唯一键增加 `extraction_generation_id` + **`level_desc`（或 stage_seq）**：同一能力（如"雷系修为"）的多个升级阶段必须能并存（初阶/中阶/高阶各一行），不能只按能力名去重 |
| character_appearance | 代际事实表 | project_id + source_id + chapter_no + canonical_name | 唯一键增加 `extraction_generation_id` |
| event_timeline | 代际事实表 | （无唯一约束） | 增加 `extraction_generation_id`，同代按 event_title+chapter 去重 |

规则：**主档只合并不隔离（但支持快照回滚），事实表按代隔离**。不能只加 `extraction_generation_id` 列就完事——必须按上表逐表迁移唯一约束。

### 4.4 人工数据兼容规则

- `origin = manual` 的数据**始终可见**，不随 generation 过滤；
- `llm_extracted / rule_extracted` 读取当前 active generation；
- 聚合查询仍按人工优先级覆盖自动抽取（manual > fanfic > original，沿用现有 canon_level/source_priority）；
- QA 的 active-generation 过滤**集中到统一 repository/service**（`structured_knowledge_repo`），禁止各问答 SQL 自行拼接过滤条件。

### 4.5 失败 generation 保留（不丢弃已付费产出）

- 失败/中断 → 标记 `failed / abandoned`，**保留 raw_output、校验错误、进度**，允许在同一 generation 内断点续跑；
- 保留期（默认 30 天）后清理；
- 成功切换后**至少保留上一代**（`superseded`），支持人工回滚。

### 4.6 激活门槛（量化，全部满足才切 active）

1. `source_content_hash` 与当前原文哈希一致（原文未变）；
2. `split_generation_id` 与当前 active 切分代一致；
3. 所有目标章节进入明确终态（ok / accepted_failed，无 pending）；
4. 失败章节清单**已人工接受**（`accepted_failed`），否则不得激活；
5. evidence 不仅非空，还要**校验片段属于对应章节**（偏移/哈希回查）；摘要类证据明确标记 `evidence_kind=summary`；
6. 未确认别名不得悄悄拆成多个正式人物（别名命中率校验，未归并的人名单独报告）；
7. **激活与 profile 聚合更新位于同一事务**（切换即生效，无中间态）。

### 4.7 数据流

```
新抽取任务
  → 创建 extraction_generations (status=running)
  → 逐章抽取写入 extraction_chapter_state + staging 事实表（带 generation_id）
  → 全部完成 → status=validating → 校验（4.6 各项）
  → 通过 → 同事务：更新 extraction_source_state.active_generation_id + profile 聚合
         → status=active（旧代 superseded）
  → 不通过 → status=failed（保留 raw_output 支持续跑），问答继续读上一代
```

## 6. 语义定义（必须分开的字段）

### 6.1 提及 vs 出场

| 字段 | 含义 | 写入方 |
|---|---|---|
| `last_mentioned_chapter` | 最后一次**被提到**（含回忆/转述/称呼） | 规则扫描 |
| `last_appeared_chapter` | 最后一次**实际出场**（有行动/台词/状态） | LLM 抽取或人工确认 |
| `mention_count` | 被提及次数 | 规则扫描 |
| `appearance_count` | 实际出场次数 | LLM 抽取/人工确认 |

规则扫描只写提及索引；**出场记录（character_appearance）只能由 LLM 或人工确认写入**。C 级默认只有提及索引。

### 6.2 结局字段拆细（v1 的 resolved/unresolved/alive_at_corpus_end 三值混合了"证据明确度"与"生死状态"，拆开）

| 字段 | 取值 |
|---|---|
| `ending_resolution` | `explicit`（原文写明结局）/ `unresolved`（原文未交代）/ `unknown`（无法判定） |
| `life_status` | `alive` / `dead` / `missing` / `retired` / `unknown` |
| `ending_desc` | 结局描述（原文支持） |
| `ending_chapter` | 结局所在章节（explicit 时必有） |
| `ending_evidence` | 结局原文片段 |

`alive_at_corpus_end` 只能作为 `last_known_status` 的取值，**不是结局类型**。

### 6.3 能力/关系必须阶段化（已拍板，P0 按此实现）

- **能力阶段**：不用 JSON 数组。`ability_profile` 每个能力阶段一行（ability_type=cultivation_level 的多行 = 阶段序列），行内 `level_desc / chapter_no / evidence / extraction_generation_id`，唯一键含 generation。支撑"什么时候升级"的结构化排序查询；
- **关系变化**：复用 `event_timeline`（新增 `relation_type` 可选字段），关系的确立/恶化/恢复作为带类型的章节事件记录；`character_relations` 仅保存当前最新关系快照（主档，人工可覆盖）。

## 7. 目标架构（维持 v1）

```
问题
  ↓
① 结构化档案聚合查询（profile + appearance + ability + event + relation）
  ↓
② 档案能否回答？ → 能：直接生成答案（带章节引用）
  ↓ 不能（缺失/冲突/需细节）
③ 原文检索（现有 RAG，仅兜底）
  ↓
④ 合并证据 → 生成答案并标注章节
```

| 问题类型 | 优先方式 |
|---|---|
| 是谁、什么系、最后状态、关系、家庭 | 结构化档案 |
| 某章发生了什么、在哪里、能力变化 | 事件 + 出场 + 能力阶段序列 |
| 原话、场景细节、氛围、动作过程 | 原文检索 |
| 档案缺失或证据冲突 | 回退原文检索 |

回答语义纪律：**"资料最晚收录至第 3233 章（检测到若干章号缺口）。X 最后出现在第 3195 章（状态描述）。原文未写明其最终结局。"**——`last_known_status` 与 `ending_resolution` 分开表述，不暗示完整无缺。

## 8. 成本估算（修正版）

### 8.1 错误修正

v1 称"先抽 A 类只需全量一半成本"——**不成立**：莫凡几乎贯穿全书（2809/3132 个标题章节），A 级深抽 ≈ 全书扫描。正确计量单位是**按章**：

| 项 | 量 |
|---|---|
| 可解析标题章节 | 3132 章（原文末章号 3233；作者跳号 10 章已剔除、格式恢复 1 章） |
| 每章文本 | ~2500 字 ≈ 2k tokens |
| 按章抽取调用 | 每章 1 次（A/B 级出场人物一并处理）= **~3132 次**（若每批 5 章则 ~630 次请求，token 不变） |
| 输入 token | ~6.3M（2k × 3132） |
| 输出 token | ~1.3M（每章 400 tokens 抽取 JSON） |
| 合计 | ~7.6M tokens，按 ¥1-3/百万输入估 **约 ¥10-30** |

C 级出场索引 = 规则扫描，0 LLM 成本。

### 8.2 正确流程（分步实测）

1. 修正章节编号（P-1）→ 别名确认（P0）→ 输出可复现分层 CSV；
2. 按 CSV 统计 A/B 级人物涉及的**唯一章节并集**（预计 ~3100 章）；
3. **先真实抽取 50-100 章**：记录输入/输出 token、失败率、耗时、evidence 质量；
4. 用实测数据外推全量成本与时长，再决定批次大小与并发。

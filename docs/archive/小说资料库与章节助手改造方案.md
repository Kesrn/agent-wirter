# 小说资料库与章节助手改造方案

## 0. 下一阶段执行说明

资料库 AI 问答的下一阶段开发，优先参考：

```text
资料问答QueryPlanner升级技术方案.md
```

旧的 Mimo / DeepSeek 执行稿已经清理，不再作为实现依据。后端业务功能仍通过现有 LLM 配置体系调用用户当前设置的模型，包括 `get_user_llm_config`、`get_llm_provider`、用户设置页里的 provider/base_url/model_id/api_key。不要把具体开发模型名称硬编码进业务逻辑。

## 1. 改造目标

当前平台已经具备章节写作、章节记忆、角色事件、设定资料、Agent 生成等能力，但这些能力仍然偏分散：

- 章节助手能触发生成、润色、转折建议、读者视角，但后台仍主要是通用生成器。
- 章节配置已经包含角色、事件、章节大纲、明线、暗线、相关设定，但生成时还没有完全围绕“当前章节资料包”工作。
- 小说项目缺少独立资料库与 RAG 问答能力，用户无法把原文、设定集、角色资料、同人规则沉淀成可检索知识。

本次改造目标是把平台升级为：

```text
每部小说 = 一个独立知识库 + 一个章节创作工作台
```

最终用户体验应该是：

- 用户可以给每本小说建立独立资料库。
- 用户可以上传原文、设定、角色、时间线、规则等资料。
- 用户可以像问资料库一样问这本小说。
- 章节生成时，AI 自动检索当前章节相关资料。
- 生成小说前，AI 会先询问用户章节走向，而不是直接替用户决定剧情。
- 章节助手成为当前章节的智能中枢，而不是简单按钮面板。

## 2. 核心信息架构

建议将小说项目拆成四层：

```text
小说项目
  ├─ 正文层
  │   ├─ 章节
  │   └─ 版本历史
  ├─ 章节记忆层
  │   ├─ 章节大纲
  │   ├─ 明线推进
  │   ├─ 本章角色
  │   ├─ 本章事件
  │   ├─ 暗线
  │   └─ 相关设定
  ├─ 项目知识库层
  │   ├─ 上传资料
  │   ├─ 用户笔记
  │   ├─ 同人规则
  │   ├─ 全文/向量索引
  │   └─ 资料问答
  └─ AI 创作层
      ├─ 章节助手
      ├─ 资料问答
      ├─ 走向选择
      ├─ 生成草稿
      ├─ 强化改稿
      └─ 一致性检查
```

## 3. 后端改造方案

### 3.1 项目资料库模型边界

`project_sources` 不建议承载所有结构化数据。角色、角色事件、章节、章节大纲、设定、暗线已经有各自业务表，如果再全量同步到 `project_sources`，会形成双写和一致性风险。

因此 V2 方案将资料库边界收窄为：

```text
结构化资料：直接查原表
  - chapters
  - outlines
  - characters
  - character_events
  - world_entries
  - hidden_threads

非结构化资料：进入 project_sources
  - 用户上传 TXT/MD
  - 用户笔记
  - 同人规则
  - 时间线文本
  - 外部参考资料
```

新增 `project_sources`，用于保存每本小说的非结构化知识源和硬约束资料。

```text
project_sources
  id
  project_id
  title
  source_type
    - upload
    - fanfic_rule
    - timeline
    - note
    - reference
  content
  metadata
  always_inject
  created_at
  updated_at
```

说明：

- `source_type = upload`：用户上传的 TXT/MD/设定文档。
- `source_type = fanfic_rule`：同人二创约束，生成时优先级最高。
- `always_inject = true`：生成时无条件注入，不依赖 RAG 命中。
- 章节、角色、事件、设定、暗线不双写到此表，生成和问答时直接查原表。

新增 `project_source_chunks`，用于非结构化资料的全文/向量检索。

```text
project_source_chunks
  id
  project_id
  source_id
  chunk_index
  content
  embedding
  token_count
  metadata
  created_at
```

检索策略建议：

- 第一阶段优先实现全文检索。SQLite 可使用 FTS5；PostgreSQL 可使用 `tsvector`。
- 第二阶段接入真实 embedding 后，再开启向量检索。
- 当前 mock embedding 只能用于测试链路，不应作为语义检索效果的依据。
- 同人规则不走检索，按 `always_inject` 无条件加载。

### 3.2 章节设定绑定

当前 `world_entries.scope_type = chapter` 只能表达“章节级设定”，但不能表达“属于第几章”。

短期建议给 `world_entries` 增加字段：

```text
chapter_sequence_number nullable int
```

这样章节配置页的“相关设定”可以只显示：

- 全局设定：`scope_type = global`
- 本章设定：`scope_type = chapter and chapter_sequence_number = 当前章节`

长期可以改为关联表：

```text
chapter_world_entries
  project_id
  chapter_sequence_number
  world_entry_id
```

如果一个设定会跨多个章节出现，再引入关联表。

### 3.3 升级 ChapterContextService

新增服务：

```text
backend/services/chapter_context.py
```

`ChapterContextService` 不是第三套上下文系统，而是现有 `agents.workflow.context_loader_node` 和 `rag.context_loader.ContextLoader` 的升级入口。

职责划分：

```text
ChapterContextService
  - 自动聚合当前章节结构化资料
  - 加载 always_inject 同人规则
  - 调用 ProjectKnowledgeService 检索非结构化资料
  - 输出统一 prompt context

context_loader_node
  - 调用 ChapterContextService
  - 保留 selected_*_ids 精确加载能力
  - 保留旧 RAG 作为兼容兜底
```

核心方法：

```python
async def build_chapter_context(
    db,
    project_id,
    chapter_sequence_number,
    intent: str,
    user_query: str | None = None,
) -> ChapterContext:
    ...
```

返回结构建议：

```json
{
  "chapter": {
    "id": "...",
    "sequence_number": 6,
    "title": "硬刚穆卓云！",
    "content": "..."
  },
  "outline": {
    "title": "...",
    "summary": "...",
    "light_line": "..."
  },
  "characters": [],
  "character_events": [],
  "hidden_threads": [],
  "world_entries": [],
  "fanfic_rules": [],
  "retrieved_sources": [],
  "previous_chapters": []
}
```

加载规则：

- 当前章节：按 `Chapter.sequence_number`
- 章节大纲：按 `Outline.sequence_number`
- 明线：短期复用 `Outline.turning_point`
- 本章角色：从 `CharacterEvent.chapter_sequence_number` 反查角色
- 本章事件：加载当前章节全部 `CharacterEvent`
- 暗线：`HiddenThread.chapter_nums` 包含当前章节
- 本章设定：`WorldEntry.chapter_sequence_number`
- 全局设定：`WorldEntry.scope_type = global`
- 同人规则：`project_sources.source_type = fanfic_rule and always_inject = true`
- 非结构化资料：按 intent + 当前章节标题 + 角色名 + 用户补充检索 `project_sources`
- 前文：最近 1-3 章摘要或正文片段

### 3.4 新增 ProjectKnowledgeService

新增服务：

```text
backend/services/project_knowledge.py
```

职责：

```python
async def ingest_source(project_id, title, content, source_type, metadata)
async def chunk_source(source_id)
async def embed_source(source_id)
async def search(project_id, query, filters=None, limit=8)
async def answer(project_id, question)
```

资料处理规则：

- 用户上传资料后立即 chunk + embedding。
- 用户笔记、时间线、外部参考资料进入 `project_sources`。
- 同人规则可不做 embedding，但生成时必须作为高优先级上下文。
- 结构化资料不进入 `project_sources`，由 `ChapterContextService` 直接查业务表。

### 3.5 章节生成改造

当前 `full_pipeline` 可以先做轻量升级，不必一次重写 LangGraph。

#### 轻量版流程

```text
1. 章节助手点击“章节生成”
2. 前端请求独立方向接口 /chapters/{num}/directions
3. 后端 build_chapter_context，返回 chapter_goal + direction_options
4. 用户选择走向或输入自定义补充
5. 前端调用现有 /chapters/generate，带 selected_direction/user_note
6. 后端进入现有 full_pipeline
7. 生成候选稿
8. 用户采纳/修改/放弃
```

新增 `GenerateRequest` 字段：

```text
selected_direction: str | None
direction_option_id: str | None
```

新增独立接口：

```text
POST /projects/{project_id}/chapters/{sequence_number}/directions
```

响应：

```json
{
  "chapter_goal": {
    "light_line": "...",
    "characters": ["程旖", "穆白"],
    "constraints": ["不得改变已有角色事件"]
  },
  "directions": [
    {
      "id": "A",
      "title": "爽点爆发",
      "description": "主角当场打破质疑，制造强烈反差。",
      "risk": "冲突消耗较快，需要结尾留钩子。"
    }
  ],
  "context_snapshot": {
    "characters": 4,
    "events": 5,
    "hidden_threads": 1,
    "world_entries": 3,
    "sources": 8
  }
}
```

#### 完整版流程（后置）

后续可以升级为多暂停节点：

```text
context_loader
→ chapter_goal_planner
→ direction_options
→ user_direction_review
→ writer
→ refinement_options
→ user_refinement_review
→ editor
→ consistency_checker
→ human_review
```

用户参与点：

- `user_direction_review`：选择剧情走向
- `user_refinement_review`：选择强化方向
- `human_review`：最终采纳/修改/放弃

注意：完整 LangGraph 多 interrupt 会显著增加前端状态机复杂度，应在 AgentPanel 拆分后再做。

### 3.6 资料问答接口

新增接口：

```text
GET  /projects/{project_id}/knowledge/sources
POST /projects/{project_id}/knowledge/sources
POST /projects/{project_id}/knowledge/upload
POST /projects/{project_id}/knowledge/search
POST /projects/{project_id}/knowledge/ask
POST /projects/{project_id}/knowledge/sync
```

问答请求：

```json
{
  "question": "穆白第几章开始对主角态度变化？",
  "filters": {
    "source_type": ["structured", "upload", "fanfic_rule"]
  }
}
```

问答响应：

```json
{
  "answer": "...",
  "citations": [
    {
      "source_id": "...",
      "title": "第 6 章 硬刚穆卓云！",
      "snippet": "...",
      "source_type": "structured.chapter"
    }
  ]
}
```

问答检索应共享 `ChapterContextService` / `ProjectKnowledgeService` 的检索逻辑：

- 结构化问题优先 SQL 查询原表。
- 非结构化问题检索 `project_sources`。
- 同人规则作为硬约束注入，不依赖检索命中。

### 3.7 审核意见结构化

当前 Critic/Consistency 输出主要在 stream 中展示，不便沉淀。

建议新增：

```text
chapter_review_notes
  id
  project_id
  chapter_sequence_number
  source_type
    - critic
    - consistency
    - reader
  severity
    - info
    - warning
    - critical
  content
  resolved
  created_at
  updated_at
```

章节助手中的“审核意见”应读取这个表，而不是仅依赖一次性 stream。

### 4.3 章节助手 UI 升级

当前章节助手建议升级为分步工作台。

```text
章节助手
  当前章节：第 6 章 硬刚穆卓云！
  已加载：角色 4 · 事件 5 · 暗线 1 · 设定 3 · 资料 8

  主操作：
    生成本章

  快捷操作：
    找转折 · 润色当前稿 · 读者反馈 · 一致性检查

  生成流程：
    1. 确认本章目标
    2. 选择剧情走向
    3. 生成章节草稿
    4. 选择强化方向
    5. 最终审校
```

在增加走向选择前，建议先拆分 `AgentPanel.vue`：

```text
AgentPanel.vue
  ├─ AgentCommandCard.vue
  ├─ AgentQuickActions.vue
  ├─ AgentWorkflowStatus.vue
  ├─ AgentOutputPanel.vue
  └─ AgentReviewNotes.vue

composables
  ├─ useGenerationFlow.ts
  ├─ useDirectionOptions.ts
  └─ useChapterContextStats.ts
```

原因：

- 当前 AgentPanel 同时处理 UI、SSE、HITL、候选稿、picker 状态。
- 继续直接堆走向选择会让状态机过重。
- 先拆分可以降低后续多节点生成的回归风险。

#### 走向选择器

AI 返回：

```json
[
  {
    "id": "A",
    "title": "爽点爆发",
    "description": "主角当场打破质疑，制造强烈反差。",
```


```text

```

## 5. UI 风格建议

### 5.1 命名统一

建议统一使用：

- `资料库`：项目级知识库
- `章节资料`：当前章节的结构化资料
- `章节助手`：当前章节的 AI 工作台
- `更新记忆`：从正文提取结构化资料
- `资料问答`：RAG 问答

避免继续使用：

- 世界观库
- 角色库

因为这些会让用户误以为角色/设定是和章节并列的独立模块，而不是服务于当前小说和章节的资料层。

### 5.2 视觉层级

建议主工作区保持三栏：

```text
左侧：章节列表
中间：编辑器 / 章节配置
右侧：章节助手
```

项目级资料库用弹窗或独立页面，不常驻章节编辑界面。

章节助手不宜再使用大块按钮堆叠，应是：

- 顶部当前章节信息
- 一行资料统计
- 主按钮
- 紧凑快捷操作
- 当前流程状态
- 输出/候选稿/审核意见

## 6. 实施阶段

### 阶段一：章节上下文服务（基于现有结构化表）

目标：让生成真正基于当前章节资料。

任务：

- 新增 `ChapterContextService`
- 升级 `context_loader_node`，由它调用 `ChapterContextService`
- 生成前自动加载章节大纲、角色事件、暗线、设定、前文
- 同人规则如果已存在，则无条件注入
- `full_pipeline / continue / enhance / summarize` 使用章节上下文
- 前端章节助手显示“已加载资料统计”

验收：

- 生成 prompt 中能看到当前章节角色事件。
- 生成时不需要手动选择角色/设定，也能使用本章资料。

### 阶段二：AgentPanel 拆分与章节助手状态

目标：为走向选择和资料统计降低前端复杂度。

任务：

- 拆出 `useGenerationFlow`
- 拆出 `useChapterContextStats`
- 拆出章节助手主操作卡、快捷操作、输出区域
- 保持现有生成/润色/转折/读者视角行为不变

验收：

- UI 行为不变。
- 前端构建通过。
- 后续可以单独接入 direction picker。

### 阶段三：走向选择独立 API

目标：AI 生成前询问用户小说走向，但不增加 LangGraph interrupt 复杂度。

任务：

- 新增 `/chapters/{sequence_number}/directions`
- 返回 `chapter_goal`、`direction_options`、`context_snapshot`
- 前端新增走向选择器
- 用户选择后调用现有 `/chapters/generate`
- 将 `selected_direction` 和 `user_note` 注入生成 prompt

验收：

- 点击“生成本章”后，AI 先给走向，不直接生成正文。
- 用户选择走向后，生成结果明显遵循该选择。

### 阶段四：项目资料库

目标：每本小说有独立知识库。

任务：

- 新增 `project_sources`
- 新增 `project_source_chunks`
- 支持手动新增资料
- 支持 TXT/MD 上传
- 支持 chunk
- 优先支持全文检索；真实 embedding 后置
- 支持资料列表
- 同人规则支持 `always_inject`

验收：

- 每个项目资料隔离。
- 上传资料后可检索。
- 同人规则不依赖检索命中，生成时稳定注入。

### 阶段五：资料问答

目标：用户可以问这本小说。

任务：

- 新增 `/knowledge/search`
- 新增 `/knowledge/ask`
- 回答附带引用来源

## 7. 风险与注意事项

### 7.1 RAG 噪声

资料越多，检索噪声越大。

应对：

- 按 `source_type` 过滤
- 同人规则高优先级
- 当前章节角色/事件直接加载，不走向量检索
- 结构化资料优先 SQL 精确查询，不依赖 embedding
- RAG 片段数量限制
- 给每条引用加来源

### 7.2 同人规则优先级

同人创作规则不能和普通资料混在一起。

规则：

- `fanfic_rule` 默认 `always_inject = true`。
- 每次生成、润色、续写、走向建议都必须加载。
- 不依赖 embedding 检索命中。
- 如果规则过长，应先摘要压缩，但不能静默丢弃。

建议 prompt 层级：

```text
最高优先级：用户本次指令
高优先级：同人规则 / 禁止事项
中优先级：章节资料 / 角色事件 / 设定
低优先级：普通资料库检索片段
```

### 7.3 避免结构化资料双写

角色、事件、章节、设定、暗线已经有业务表，不建议自动同步到 `project_sources`。

应对：

- 结构化资料直接查原表。
- `project_sources` 只保存上传资料、用户笔记、同人规则、外部参考。
- 如果未来确实需要同步结构化资料，必须有 `sync_origin_id`、重建 chunk、幂等更新和回滚策略。

### 7.4 mock embedding 风险

当前 mock embedding 只能保证链路可跑，不能保证语义检索效果。

建议：

- 第一阶段用全文检索兜底。
- 真实 embedding 接入前，不把“智能语义检索”作为验收标准。
- 资料问答必须显示引用来源，便于用户判断可信度。

### 7.5 生成流程过长

多节点询问会提升控制感，但也会增加操作成本。

建议提供两种模式：

- 快速生成：直接生成
- 引导生成：先问走向，再生成

默认推荐引导生成。

### 7.6 前端状态机膨胀

章节助手会继续承载生成、走向选择、SSE、候选稿、审核意见、资料统计。

建议：

- 功能扩展前先拆分 `AgentPanel.vue`。
- 流程状态放入 composable。
- UI 组件只负责展示和触发。
- 走向选择先用独立 API，不直接增加 LangGraph 多 interrupt。

## 8. 推荐优先级

最推荐先做：

```text
1. ChapterContextService（基于现有结构化表）
2. AgentPanel 拆分 + 章节助手资料统计
3. 生成前走向选择独立 API
4. 项目资料库基础表（上传资料 / 同人规则 / 用户笔记）
5. 资料问答（结构化 SQL + 非结构化检索）
6. 完整多节点 LangGraph 工作流
7. 结构化审核意见
```

原因：

- `ChapterContextService` 可以先利用现有表落地，不依赖资料库新表。
- 先拆 AgentPanel，可以降低后续走向选择和多节点流程的前端风险。
- 走向选择用独立 API，能最快提升小说生成体验，同时避开多 interrupt 复杂度。
- 项目资料库先只做非结构化资料和同人规则，避免结构化数据双写。
- 资料问答复用同一套上下文和检索逻辑，避免重复实现。

## 9. 最终效果

完成后，平台能力会从：

```text
AI 帮我写一章
```

升级为：

```text
AI 理解我这本小说，知道每章发生了什么，能查资料、问设定、控角色，并在关键剧情节点询问我的创作选择。
```

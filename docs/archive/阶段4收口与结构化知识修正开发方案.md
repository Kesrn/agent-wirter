# 阶段 4 收口与结构化知识修正开发方案

## 0. 当前状态

当前分支：`novel-extraction-mvp`

当前工作区存在一批未提交的“阶段 4 抽取质量修复”改动，涉及：

- `backend/services/extraction_normalization.py`
- `backend/services/extraction_service.py`
- `backend/services/magic_systems.py`
- `backend/services/structured_qa.py`
- `backend/tests/test_extraction.py`

这批改动目标是修复真实 20 章抽取暴露出的 4 个 P1 问题：

1. 能力名称重复：`雷系星尘`、`雷霆系魔法`、`火系星尘` 等需要归一为标准法系。
2. 人物别名重复：`张侯`、`张候`、`张小候`、`张小侯` 应合并为同一角色。
3. 能力误归因：介绍性台词里的 `风之翼` 不应归到莫凡名下。
4. 世界规则分类碎片化：`魔法修炼体系`、`魔法修炼机制` 等应归入有限白名单。

本轮不要直接上 embedding、Qdrant、GraphRAG、reranker，也不要扩到全书抽取。先把结构化知识质量和人工纠错闭环做稳。

## 1. 本阶段目标

本阶段分两步：

第一步：阶段 4 质量修复收口。

- 验证当前未提交修复是否真实有效。
- 用 20 章样本做 QA 实测。
- 确认无明显回归后提交。

第二步：结构化知识人工修正能力。

- 支持用户对人物、能力、事件、世界规则进行增删改查。
- 用户手动修正的结构化知识优先级高于 LLM 抽取和规则抽取。
- 修改必须保留来源、证据、优先级、canon level，避免“改完以后不知道从哪来的”。

## 3. 第二部分：结构化知识人工修正

### 3.1 为什么下一步先做人工修正

真实 LLM 抽取一定会有错误，包括：

- 人物别名没合并。
- 能力误归因。
- 事件抽取太粗或太细。
- 世界规则把剧情成就误当规则。

如果没有人工修正能力，用户只能反复重抽、调 prompt、调规则，永远无法稳定把资料库修到可用状态。

所以本阶段不先做 embedding，而是先让正式结构化库可编辑、可纠错、可追溯。

### 3.2 后端 API 范围

需要支持 4 类结构化表：

- `character_profile`
- `ability_profile`
- `event_timeline`
- `world_rule`

需要提供统一 CRUD 能力。

建议路由形式：

```text
GET    /api/projects/{project_id}/knowledge/structured/{table}
POST   /api/projects/{project_id}/knowledge/structured/{table}
PATCH  /api/projects/{project_id}/knowledge/structured/{table}/{record_id}
DELETE /api/projects/{project_id}/knowledge/structured/{table}/{record_id}
```

其中 `{table}` 只允许：

```text
characters
abilities
events
world_rules
```

不要允许任意表名透传到 SQL。

### 3.3 手动修正字段规则

用户手动新增或编辑的记录必须写入：

```text
origin = "manual"
canon_level = "manual"
source_priority = 100
```

如果是编辑已有 LLM 抽取记录：

- 不要丢弃原 evidence。
- 追加一个 manual evidence 或 edit note。
- 保留原始来源信息，便于以后追溯。

建议新增字段或 metadata：

```json
{
  "edited_by_user": true,
  "manual_note": "...",
  "previous_origin": "llm_extracted"
}
```

如果现有模型字段不完全支持，可先放入 `metadata_` 或等价 JSON 字段。

### 3.4 删除规则

删除结构化记录时，MVP 可以先物理删除，但必须限制作用域：

- 必须同时校验 `project_id`
- 必须校验当前记录属于该项目
- 不能跨项目删除

如果已有 soft delete 机制，优先使用 soft delete。

### 3.5 QA 优先级规则

结构化 QA 查询时，排序优先级必须是：

```text
manual > fanfic > original
source_priority 高 > 低
confidence 高 > 低
updated_at 新 > 旧
```

用户手动修正后，QA 必须优先采用手动记录。

验收样例：

1. 原抽取记录：`莫凡 - 雷系`
2. 用户手动新增：`莫凡 - 冰系`，`canon_level=manual`
3. 用户问：`莫凡有什么系别？`
4. 回答中必须包含手动设定，并且标明是手动资料。

注意：这只是优先级测试，不代表业务上莫凡真的有冰系。

## 4. 前端 UI 范围

在 `NovelExtraction.vue` 或现有结构化结果面板中增加编辑能力。

### 4.1 列表操作

每条结构化记录显示：

- 编辑
- 删除
- 查看 evidence

不要做复杂弹窗套弹窗。MVP 可以使用右侧编辑面板或简单 modal。

### 4.2 新增入口

每个 tab 提供新增按钮：

- 新增人物
- 新增能力
- 新增事件
- 新增世界规则

新增记录默认：

```text
origin = manual
canon_level = manual
source_priority = 100
confidence = 1.0
```

### 4.3 编辑表单字段

人物：

- name
- aliases
- identity_desc
- status
- evidence/manual_note

能力：

- character_name
- ability_type
- name
- level
- status
- evidence/manual_note

事件：

- title
- description
- characters
- location
- importance
- evidence/manual_note

世界规则：

- category
- rule_text
- priority
- evidence/manual_note

字段名以实际模型为准，不要为了 UI 强行改数据库字段。

### 4.4 交互验收

必须支持以下页面流程：

1. 打开 novel 资料详情。
2. 查看结构化抽取结果。
3. 编辑一个人物身份，保存后列表立即刷新。
4. 新增一条能力，保存后 QA 能查到。
5. 删除一条误抽能力，QA 不再回答该能力。
6. 点击 evidence 能看到证据文本或 manual note。

## 7. 禁止事项

本阶段禁止做：

- 不要接 embedding。
- 不要接 Qdrant。
- 不要做 GraphRAG。
- 不要做全书 3000 章抽取。
- 不要引入新的任务队列。
- 不要把具体小说角色继续硬编码进通用逻辑。
- 不要让 LLM 自动覆盖用户手动修正。
- 不要删除原文资料、chunks、QA 历史。

## 9. 下一阶段预告

本阶段完成后，下一阶段再考虑：

1. 通用 alias 表与人工确认别名。
2. 关系、阵营、地点、伏笔等结构化表。
3. 结构化 QA 扩展到人物档案、关系变化、事件时间线。
4. 最后才是 embedding + hybrid retrieval + reranker。

不要跳过人工修正直接进入向量化。否则错误结构化数据会被向量索引放大，后面更难清理。

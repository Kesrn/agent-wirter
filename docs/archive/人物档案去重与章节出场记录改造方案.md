# 人物档案去重与章节出场记录改造方案

## 0. 背景

当前小说逐章结构化抽取已经能跑通，但出现一个必然问题：

如果同一个人物每章都出现，LLM 每章都会抽到这个人物。

这在 staging 层是正常的，因为 staging 表示“本章观测到的信息”。但正式结构化知识库不能每章都新增或无限膨胀同一个人物档案。

正确设计应该是：

```text
每章抽取结果：
  莫凡本章出现了
  莫凡本章做了某事
  莫凡本章状态有变化

正式人物档案：
  莫凡只有一条 character_profile
  只保存稳定身份、别名、当前状态、关键证据、统计信息

章节出场记录：
  第1章 莫凡出现
  第2章 莫凡出现
  第3章 莫凡出现
```

本阶段目标：把“人物档案”和“章节出场记录”拆开，避免主角出现 3000 章后把 `character_profile.evidence` 塞爆。

## 1. 当前问题

### 1.1 现在可能出现的问题

1. 同一人物每章都被抽到。
2. merge 层如果只按 name 合并，会不断追加 evidence。
3. `character_profile` 可能变成几千条 evidence 的大 JSON。
4. QA 查询人物档案时会拿到大量重复出场证据。
5. 人物列表 UI 会变慢，且信息不可读。

### 1.2 正确原则

```text
staging 可以重复。
正式人物档案不能重复。
普通出场不应该无限写入人物档案 evidence。
人物出场应该进入 appearance 表。
人物档案只在身份、状态、别名、重要信息变化时更新。
```

## 2. 本阶段目标

实现：

1. 新增 `character_appearance` 表。
2. 每章人物出现写入 `character_appearance`。
3. `character_profile` 保持一人一档。
4. 限制 `character_profile.evidence` 数量。
5. 增加人物统计字段：
   - `first_seen_chapter`
   - `last_seen_chapter`
   - `appearance_count`
6. UI 展示人物出现统计，不再把普通出场证据全堆在人物档案里。

本阶段不要做：

- 不做关系图谱。
- 不做 embedding。
- 不做复杂别名审核 UI。
- 不改 LLM 抽取 schema 大结构。
- 不删除已有正式人物数据。

## 3. 数据库改造

### 3.1 character_profile 补字段

给 `character_profile` 增加：

```sql
first_seen_chapter INT NULL;
last_seen_chapter INT NULL;
appearance_count INT NOT NULL DEFAULT 0;
important_evidence JSONB DEFAULT '[]';
```

说明：

- `first_seen_chapter`：首次出现章节。
- `last_seen_chapter`：最近出现章节。
- `appearance_count`：累计出现次数。
- `important_evidence`：关键证据，区别于普通出场 evidence。

如果暂时不想加 `important_evidence`，也可以复用 `evidence`，但必须限制长度。

### 3.2 新增 character_appearance 表

新增模型：

```python
class CharacterAppearance(UUIDMixin, TimestampMixin, Base):
    __tablename__ = "character_appearance"

    project_id = mapped_column(GUID(), index=True, nullable=False)
    source_id = mapped_column(GUID(), index=True, nullable=False)
    chapter_id = mapped_column(GUID(), index=True, nullable=True)
    character_id = mapped_column(GUID(), ForeignKey("character_profile.id"), index=True, nullable=True)

    character_name = mapped_column(String(255), index=True, nullable=False)
    canonical_name = mapped_column(String(255), index=True, nullable=False)
    chapter_no = mapped_column(Integer, index=True, nullable=False)
    chapter_title = mapped_column(String(500), nullable=True)

    role_in_chapter = mapped_column(String(100), nullable=True)
    summary = mapped_column(Text, nullable=True)
    evidence_text = mapped_column(Text, nullable=False)
    importance = mapped_column(Integer, default=2)
    confidence = mapped_column(Float, default=0.8)

    origin = mapped_column(String(50), default="llm_extracted")
    canon_level = mapped_column(String(50), default="original")
```

### 3.3 唯一约束

建议加唯一约束：

```text
project_id + source_id + chapter_no + canonical_name
```

作用：

- 同一章同一人物只保留一条 appearance。
- 重抽该章时可以 upsert 或先删后写。

## 4. Merge 层改造

重点文件：

- `backend/services/extraction_service.py`
- `backend/services/extraction_normalization.py`
- `backend/models/structured_knowledge.py`
- 新增 migration
- 新增 tests

### 4.1 人物 merge 原则

当前 LLM 抽出的 `characters[]` 进入正式库时：

1. 先用 `normalize_character_name` 得到 canonical_name。
2. 查找已有 `CharacterProfile`：
   - project_id + canonical name
   - aliases 命中也应合并，若已有别名机制则复用。
3. 如果不存在，创建人物档案。
4. 如果存在，只更新必要字段。
5. 无论是否更新档案，都写入/更新 `CharacterAppearance`。

### 4.2 什么情况下更新 character_profile

只有以下情况才更新人物档案：

1. 新人物首次出现。
2. 新 alias 出现。
3. identity 原为空，新抽取有明确 identity。
4. status 有明确变化。
5. importance 较高。
6. evidence 体现身份/状态/设定变化，而不是普通出场。

普通出场不要追加到 `character_profile.evidence`。

### 4.3 evidence 限制规则

给人物档案 evidence 设置上限。

建议：

```python
MAX_CHARACTER_PROFILE_EVIDENCE = 20
```

规则：

- `character_profile.evidence` 只保留前若干关键证据 + 最近关键证据。
- 普通出场证据进入 `character_appearance.evidence_text`。
- 不要无限 append。

简单可实现版本：

```python
def append_limited_evidence(existing, new_item, max_items=20):
    if not new_item:
        return existing or []
    items = list(existing or [])
    if new_item in items:
        return items
    items.append(new_item)
    if len(items) > max_items:
        items = items[:10] + items[-10:]
    return items
```

### 4.4 appearance 写入规则

每次 merge 一个 character extraction 时，都写 appearance：

```text
project_id
source_id
chapter_no
chapter_title
character_id
character_name = 原抽取名
canonical_name = 归一名
summary = new_info 或 本章角色摘要
evidence_text = evidence
importance
confidence
origin
canon_level
```

如果同一章同一 canonical_name 已存在：

- 更新 summary/evidence/confidence/importance。
- 不新增重复记录。

### 4.5 profile 统计字段更新

每次 appearance upsert 后，刷新人物档案：

```text
first_seen_chapter = min(existing, chapter_no)
last_seen_chapter = max(existing, chapter_no)
appearance_count = count(character_appearance where project_id + canonical_name)
```

性能上 MVP 可以每次 count，后续再优化。

## 5. reset / delete 逻辑

### 5.1 reset_extraction

`reset_extraction` 必须删除当前 source 的：

- ExtractionJob
- ExtractionStaging
- CharacterProfile
- AbilityProfile
- EventTimeline
- WorldRule
- CharacterAppearance

注意：

- 只删当前 `project_id + source_id` 对应数据。
- 如果 CharacterProfile 未来可能跨 source 合并，当前 MVP 可继续按 source/project 清理，但必须测试覆盖。

### 5.2 delete project/source

删除项目或资料源时，也要删除 `character_appearance`。

## 6. API 改造

### 6.1 结构化列表返回人物统计

现有：

```text
GET /api/projects/{project_id}/knowledge/structured/characters
```

人物 item 增加：

```json
{
  "first_seen_chapter": 1,
  "last_seen_chapter": 12,
  "appearance_count": 8
}
```

### 6.2 人物出场列表接口

新增：

```text
GET /api/projects/{project_id}/knowledge/characters/{character_id}/appearances
```

或：

```text
GET /api/projects/{project_id}/knowledge/structured/characters/{character_id}/appearances
```

返回：

```json
{
  "items": [
    {
      "chapter_no": 1,
      "chapter_title": "第1章 ...",
      "summary": "...",
      "evidence_text": "...",
      "importance": 2,
      "confidence": 0.9
    }
  ],
  "total": 8
}
```

支持：

- `limit`
- `offset`
- 按 chapter_no 排序

## 7. 前端改造

文件重点：

- `frontend/src/components/NovelExtraction.vue`
- `frontend/src/api/client.ts`

### 7.1 人物列表展示

人物卡片增加：

```text
首次：第 X 章
最近：第 Y 章
出场：N 次
```

### 7.2 evidence 展示调整

人物卡片中不要展示一堆普通出场 evidence。

建议显示：

- 身份
- 状态
- 别名
- 首次/最近/出场次数
- 关键证据 1 条
- “查看出场记录”按钮

### 7.3 出场记录面板

点击“查看出场记录”后：

- 可以用展开区域或 modal。
- 显示该人物的章节出场列表。
- 每条显示 chapter_no、summary、evidence_text。

MVP 不要求分页 UI 很复杂，但接口要支持 limit/offset。

## 9. 验收标准

可认为完成的标准：

- 同一人物跨章节不会生成多条 `character_profile`。
- 跨章节出场会写入 `character_appearance`。
- 人物 profile 有 first_seen / last_seen / appearance_count。
- profile evidence 不会无限增长。
- UI 能查看人物出场记录。
- reset/delete 会清理 appearance。
- 后端全量测试通过。
- 前端 build 通过。

## 10. 禁止事项

本阶段禁止：

- 不要上 embedding。
- 不要扩关系/阵营/地点/伏笔。
- 不要引入复杂 GraphRAG。
- 不要让每章普通出场继续塞进 profile evidence。
- 不要硬编码具体小说人物。
- 不要破坏现有人工修正 CRUD。

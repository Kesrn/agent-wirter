## 2. 三个关键发现

### 发现 A：137/140 次生成开着提示词优化器（`prompt_optimizer = True`）

```
prompt_optimizer        : {False: 3, True: 137}
prompt_optimizer_model  : xai/grok-4.5  (140/140)
optimize_on_run         : {False: 140}
```

- `optimize_on_run = False` 表示**不会自动跑**，即：是**手动点「优化提示词」按钮**触发的，结果回填进 prompt 框，然后提交。
- 优化器模型固定为 `xai/grok-4.5`，API 走 `https://llm.runninghub.ai`。

**后果**：用户手写的 prompt 实际不是发给模型的文本，**Grok 改写后的长文才是**。

### 发现 B：优化后的 prompt 长度 1884–12774 字符（中位 4771）

```
optimizer = True  :  n=137   min=1884  中位=4814  max=12774
optimizer = False :  n=3     [1192, 1192, 2462]
```

其中 **131 份含完整六段式字段**：

```
subject_definitions   131 / 140
retention_analysis    131 / 140
detailed_description  131 / 140
overall_soundscape    132 / 140
non_diegetic_music    132 / 140
[Shot 1]              118 / 140
<Subject N>           131 / 140
```

用户手写的那三份（1192 / 1192 / 2462 字符）**没有任何六段式字段**。

> **即：中文速查表里的六段式，不是你在写，是 Grok 在写。**
> 这解释了「三种差别极大的提示词 → 同一个失败模式」：它们的差别在优化阶段就被抹平了，出来的都是同一套结构的 4000 字长文。

### 发现 C：参考视频传进去了，但提示词里 0 次引用

```
真传了参考视频的样本：111 / 140
其中 prompt 含 "<Video" 的：0 / 111
```

素材接入实况（`media_map` 逐个节点追溯）：

| 素材构成 | 样本数 |
|---|---|
| 3 音频 + 3 图片 + 3 视频 | 56 |
| 3 音频 + 4 图片 + 3 视频 | 23 |
| 3 音频 + 4 图片（无视频） | 13 |
| 其余组合 | 48 |

`LoadVideo` 节点确实挂了真实文件（例：`d21540e3...696c90.mp4`，`keep_audio: true`），并且 `media_4 = ["43", 0]` 真的接到了 `MiniMaxH3Easy`。

**但优化后的 prompt 里，引用编号 `__MINIMAX_H3_REF_N__` 最大只到 6，且 `(1,2,3)` 占 68 个** —— 编号体系只覆盖**图片**，3 个视频槽和 3 个音频槽从未被任何一条 prompt 引用。

### 附：任务类型分布

```
[reference generation]        129 / 140
first frame continuation        2 / 140
(无标记)                        9 / 140
```

**129 份是「参考生成」**（图驱动）。140 份里只有 **6 份**出现 "replace" 字样 —— 即真正的「换人」尝试在语料里是极少数。

## 3. 根因链（修正版）

```
你手写短 prompt（60–400 词）
        ↓
点了「优化提示词」按钮  ← 真正的分叉点
        ↓
Grok-4.5 输出 4000+ 字符六段式长文
  · detailed_description 把每个动作、镜头、台词写死
  · 编号体系只认图片，参考视频不在其中
        ↓
提交给 H3 的文本 = 长文（视频从未被引用）
        ↓
模型按文字演 → 「自由发挥」
```

**这不是模型能力不足，也不是素材没传**（这两条我此前都判断过，均被本次数据推翻/修正）。

## 4. 修正清单（按优先级）

### P0 —— 关掉优化器

`MiniMaxH3Easy` 节点：

| 参数 | 现状 | 改为 |
|---|---|---|
| `prompt_optimizer` | `True`（137/140） | **`False`** |
| `prompt_optimizer_optimize_on_run` | `False` | 保持 `False` |

**同时**：以后贴完 prompt 后，**不要点「优化提示词」按钮**。若手滑点了，检查 prompt 框是否被 4000 字长文覆盖 —— 覆盖了就撤回。

### P0 —— prompt 里用官方序号标签引用视频

现状三份手写 prompt 分别用了 `@视频一`（1192 字符版）和 `the reference video`（自然语言），`reference_mention_mode` 是 **`index`** —— 该模式要求用**序号标签**，官方写法是 `<Video 1>`。

> 此条为**高置信推断**（依据：官方 ref-en.txt 全文用 `<Video N>`；节点参数名 `reference_mention_mode` 取值 `index` 指向序号寻址）。需一次对照实验坐实。

改写后的 prompt（维持注意力优先四句，但把引用改成标签）：

```
Reproduce <Video 1> exactly with two new performers.
<Subject 1> is the woman from <Picture 1>; <Subject 2> is the man from <Picture 2>.
Both keep their own outfits; only the appearances are replaced, motions follow <Video 1>.
Reproduce <Video 1> exactly — same choreography, same timing, same camera, same set.
```

### P1 —— 时长收短

```
seconds: 15.0 → 67 个    10.0 → 23 个    12.0 → 15 个
```

参考视频在 15 秒上做逐拍跟随几乎不可能。**建议先砍到 6–8 秒**验证跟随能力，通了再放长。

### P1 —— 分辨率

```
resolution: 480P → 117 个    720P → 23 个
```

跟随类任务优先用 **720P**。

### P2 —— 素材精简

`media` 接入 9–12 个素材的样本占主流。**跟随类任务只留：1 个参考视频 + 2 张人物图**，其余槽位清空。

## 5. 验证顺序（一次只改一个变量）

| # | 变更 | 观察点 |
|---|---|---|
| 1 | `prompt_optimizer = False`，其余不动，提交同一份手写 prompt | prompt 框是否保持原文（证明优化器是分叉点） |
| 2 | 用第 4 节改写版（`<Video 1>` 标签） | 动作是否开始跟随 |
| 3 | `seconds` 收到 6–8s | 跟随是否变稳 |
| 4 | `resolution` → 720P | 细节是否变好 |

第 1 步就能给出决定性答案：**如果关掉优化器后跟随立刻改善，根因即锁定。**

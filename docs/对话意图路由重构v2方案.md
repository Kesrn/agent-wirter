# 对话意图路由重构 v2.4 —— LLM 理解主导 + 规则安全护栏

> 状态：方案 v2.4（已补齐前端 unsupported 状态与 plan.target 类型契约，可进入实现）
> 关联：对话式创作（Conversation Creative Assistant）
> 原则：LLM 是理解大头，规则是安全护栏；任务卡 + 人工确认是最终安全边界。

---

## 0. 背景与问题（v1 实测确认）

| # | 问题 | 证据 |
|---|------|------|
| 1 | LLM 兜底形同虚设 | `classify_with_llm` 开头 `if confidence >= 0.7: return rule_result`，而规则对任意输入恒返回 0.9~0.95 → LLM 永不触发 |
| 2 | 规则猜不透自然语言 | "把主角写得更强一点""帮我改改" → discussion |
| 3 | 目标对象也是规则 | `_resolve_rewrite_target` 只认"第N章"正则 / 前端上下文 |
| 4 | 无多轮上下文 | `classify_intent(user_id, content, db)` 看不到最近对话与当前工作对象 |
| 5 | 复合任务无单一权威 | 规则拆 steps 后 LLM 又改顶层 intent → 结构矛盾 |
| 6 | 流程控制误判风险 | 纯关键词包含判断，"不要撤销"会误入 flow_control |

## 1. 目标架构

```
用户输入
  │
  ├─ A. 流程控制预筛（规则，安全第一）
  │     ├─ 否定词 / 疑问语气 / 讨论语境 → 不直达，走 LLM 理解
  │     ├─ 当前无可撤销/可采用对象 → 不直达，走 LLM 理解（或明确提示）
  │     └─ 通过 → 规则直达 flow_control（不调 LLM）
  │
  ├─ B. LLM 理解（主路径，严格结构化输出）
  │     {intent, operation, target_scope, target_chapter_no,
  │      mentioned_entities, requirements[], needs_clarification,
  │      clarification_question, plan{steps[], dependencies[]}}
  │     （无 requires_confirmation——由后端计算，见补锁 1）
  │     ├─ 输入：当前消息 + 最近 N 轮 + 当前工作对象 + 已确认约束
  │     ├─ 成功 → 规则护栏校验 → 采用
  │     └─ 失败（无 Key / 超时 / 非法 JSON / 校验不过）→ 规则回退
  │
  └─ C. 规则护栏（两层）
        - 结构校验：Pydantic 严格模型，非法字段一律拒绝
        - 业务校验：目标章节必须真实存在；意图白名单
        - 最终安全边界：任务卡展示目标 → 用户确认 → 生成 → 人工采用
```

## 2. 评审补锁的五项实现细节（v2.1）

> v2 评审确认：总体架构可批准，但开工前必须补锁以下 5 项，
> 尤其是第 2、4 项——否则"理解得更准"不会传导到最终生成。

### 补锁 1：`requires_confirmation` 由后端计算，不信任 LLM

**LLM 不输出 `requires_confirmation` 字段**（从 `LLMIntentOutput` 中移除 + `extra="forbid"` 严格拒绝
多余字段——即使 LLM 强行输出该字段也会校验失败回退规则，杜绝误用）；
`needs_clarification` 仅作**建议**：

```
LLM 只负责理解
后端负责计算 requires_confirmation（按风险等级）
后端负责最终是否需要澄清（结合目标校验）
前端负责展示并等待用户操作
```

- `rewrite` / `data_operation` / `flow_control` → 后端强制 `confirmation_required=True`（L2 及以上），即使 LLM 返回 `false`
- `needs_clarification` 仅当 LLM 建议 + 后端目标校验失败（无章节/章节不存在/实体缺失）时采纳，最终以后端校验为准

### 补锁 2（P0）：LLM 解析结果必须写入任务卡并传入生成 Prompt

现状缺口（已核实）：`_build_task_card` 只保存 `constraints.user_instruction = 原始消息`，
`_generate_candidate` 也只读它——LLM 理解结果不会传导到生成。

任务卡扩展为：

```json
{
  "user_instruction": "按刚才第二种方案改",
  "resolved_instruction": "采用上一轮提出的第二种方案：加强主角在冲突场景中的压迫感",
  "operation": "strengthen_character_portrayal",
  "mentioned_entities": ["主角"],
  "router_source": "llm",
  "prompt_version": "intent-router-v2",
  "context_snapshot": {"chapter_no": 1, "version_id": "...", "selected_text": "..."}
}
```

- **`resolved_instruction` 生成来源（方案 A，已选定）**：LLM 只输出**结构化字段**，
  后端按模板组装具体指令文字，避免 LLM 输出大段不可控解释：

  ```json
  {
    "operation": "strengthen_character_portrayal",
    "mentioned_entities": ["主角"],
    "requirements": ["加强冲突场景中的压迫感", "保持人物关系不变"]
  }
  ```

  后端组装示例：`"围绕主角（mentioned_entities）执行 strengthen_character_portrayal：加强冲突场景中的压迫感；保持人物关系不变"`。
  模板按 operation 类型映射（未匹配 operation 时回退原始消息）。
- `_build_task_card` 接受 LLM 结果，把 `resolved_instruction / operation / mentioned_entities / requirements / context_snapshot` 写入任务卡；任务卡同时保留原始 `user_instruction` 便于追溯
- `_generate_candidate` 的 prompt 组装：`user_instruction` 优先用 `resolved_instruction`，没有则回退原始消息
- 任务卡存根（`GenerationRecord.request_params`）同样携带 `router_source / prompt_version`，便于溯源

### 补锁 3：明确上下文装载为"5 个回合 = 最多 10 条消息" + 选中文本

- 明确语义：**最近 5 个 user-assistant 回合**。取数保证成对：
  - 先按 `created_at DESC` 找最近 5 条 **user** 消息；
  - 再通过 `reply_to_id` 补齐对应 **assistant** 消息（跳过未完成的占位消息）；
  - 上限 10 条。**不得用裸 `LIMIT 10`**（可能取到 10 条 user 消息或占位消息，不成对）
- 工作对象上下文不止正文前 500 字，扩展为：
  - 当前章节号 / 标题 / 版本号 / 当前任务卡
  - 用户选中的文本（`selection`）
  - 光标所在段落（`current_paragraph`）
  - 已确认约束（must_preserve / must_not_change）
- 前端 `ConversationContext` 增加 `selection` / `current_paragraph` 字段（现有 `context` 透传通道已具备）

### 补锁 4：复合任务超出能力时明确拒绝，不得偷偷执行

当前能力边界（第一版）：仅单章重写；knowledge_query 不接 RAG；data_operation 不执行。

复合任务行为采用**方案 B（识别但拒绝执行）**：

```
LLM 可以识别出完整 steps（保留完整 plan）
但只要 steps 中包含当前不支持的能力（knowledge_query / data_operation / flow_control）：
→ 保留完整 plan
→ 返回 intent_unsupported
→ 不生成 rewrite 任务卡（task_card = null）
→ 不执行任何一步（绝不"识别出查询步骤却偷偷只执行修改步骤"）
→ 提示："当前暂不支持自动执行多步任务，请先完成知识查询，再确认修改任务。"
```

验收断言（沿用现有契约——`intent` 保持五类枚举之一 + `intent_unsupported` 布尔标记，
与现有 flow_control 定稿拒绝路径一致）：

```json
{
  "intent": "rewrite",
  "intent_unsupported": true,
  "unsupported_reason": "当前暂不支持自动执行多步任务，请先完成知识查询，再确认修改任务。",
  "plan": {"plan_id": "...", "steps": [{"intent": "knowledge_query"}, {"intent": "rewrite"}], "dependencies": [...]},
  "task_card": null,
  "requires_confirmation": false
}
```

> 不扩展 `ConversationIntent` 枚举（避免前端五处类型分支全部改动）；
> `intent` 取 plan 中已支持能力的主意图（全 rewrite → rewrite），
> `intent_unsupported=true` 明确告知不可执行。

**前端必须同步处理 unsupported 状态（P0 契约）**——已核实当前缺口：
- `ConversationSendMessageResponse` 缺少 `intent_unsupported?: boolean` 与 `unsupported_reason?: string | null` 字段（`api/chat.ts:85` 现无此二字段）
- `api/chat.ts:276` 的 `intent_unsupported` 只是 HTTP **错误码**映射（`ChatApiError`），**不是**成功响应体字段处理
- `useConversationStore.sendMessage()` 只看 `task_card / requires_confirmation / clarification` 三字段——`task_card: null + intent_unsupported: true` 会错误进入 `idle` 并显示"已为你整理任务卡"默认文案

前端改动（纳入实施范围）：
```ts
export interface ConversationSendMessageResponse {
  // ...现有字段
  intent_unsupported?: boolean
  unsupported_reason?: string | null
}
```
Store 增加分支：`res.intent_unsupported` 为 true 时 → `awaiting='idle'` + `error=unsupported_reason`（或独立提示态），**不得静默回空闲**。

仅当所有步骤都在已支持能力内（全部 rewrite）才生成计划与任务卡。
Pydantic 模型已嵌入 `LLMIntentOutput.plan`（见决策 5），统一 1-based 编号 +
有向无环校验：依赖下标必须指向存在的 step、`from_step != to_step`、无环。

### 补锁 5：规则降级路径同步支持否定 / 疑问 / 可用动作集合

不能只在 LLM 路径加预筛——**无 Key 时规则回退也必须正确处理**"不要撤销，继续修改"。

- `classify_rule` 内部先做否定/疑问检测：
  - 含否定词（不要/先别/不能/不该/别）且同时含流程控制词 → 不是 flow_control，继续走改写/讨论判定
  - 含疑问/讨论语气（该不该/为什么/讨论/？）且含流程控制词 → discussion
- `has_actionable_state` 单布尔升级为动作集合：

```python
available_actions: set[str]   # {"accept", "discard", "revert"}
```

- 流程控制直达条件：命中流程词 && 无否定 && 无疑问 && 对应动作在 `available_actions` 中
- "有可回滚对象"≠"有可采用候选稿"——分别对应 revert / accept 的可用性

## 2. 六项锁死决策（评审要求）

### 决策 1：目标章节优先级（显式 > 上下文 > LLM 推断 > 澄清）

```text
1. 用户显式写出的章节号（"第 N 章"）        ← 最高，LLM 不得覆盖
2. "本章/这章/这章" 对应的前端当前章节       ← 次高
3. LLM 根据对话推断的章节                  ← 仅补充隐含目标
4. 无法确定 → 澄清（"请问要修改第几章？"）
```

边界：
- **LLM 未返回目标**（`target_chapter_no: null`）→ 允许回退到当前章节（当用户在操作当前章语境）
- **LLM 返回了不存在的目标**（如第 99 章）→ **必须澄清，绝不偷偷回退当前章节**（防 LLM 幻觉改错章）

实现：`_resolve_rewrite_target` 改为接收四层来源，按上述优先级合并；DB 存在性校验作为硬门槛。

### 决策 2：分类器接入多轮上下文与当前工作对象

签名变更：

```python
async def classify_intent(
    user_id: str,
    content: str,
    db: AsyncSession,
    *,
    workspace_context: ChatWorkspaceContext | None,   # 当前选中章节/正文/版本
    recent_messages: list[ChatMessageRecord],          # 最近 3~5 轮（含任务卡、澄清、确认）
    confirmed_constraints: list[str],                  # 已确认约束（must_preserve/must_not_change）
) -> IntentResult
```

装载范围（防上下文无限增长，与补锁 3 统一）：
- 最近 5 个 user-assistant 回合（先取 5 条 user 消息，再按 reply_to_id 补齐 assistant，上限 10 条）
- 当前章节：`chapter_no / title / version_id / 当前任务卡 / 已确认约束`
- 用户选中文本（`selection`）、光标所在段落（`current_paragraph`）
- 正文**不传完整稿**：必要时传摘要；所有文本字段限制最大长度

这样"按刚才第二种方案改""就改这章""这一段保留，后面压缩"才有信息可依。

### 决策 3：复合任务单一权威计划源

**推荐：LLM 一次性输出完整 `steps[]` 与依赖**。检测到复合信号（连接词/多动作）时：
- LLM prompt 要求输出 `steps: [{intent, raw, target_chapter_no}]` + `dependencies`
- **顶层 `intent` 由 LLM 根据 steps 汇总**（含 rewrite 步 → rewrite）
- 规则 `_split_compound_steps` 仅作降级（LLM 不可用时）

同时修复现成 bug：`_split_compound_steps` 的 `second = clean[pos + 1:]` 只跳过一个字符，须按连接词全长跳过（`"然后"` 跳 2、`"接着"` 跳 2、`"再之后"` 跳 3）。

不再允许"规则生成 plan + LLM 改顶层 intent"双权威。

### 决策 4：流程控制规则支持否定 / 疑问 / 状态校验

流程控制预筛（规则，不调 LLM）增加：

```python
def _flow_control_passthrough(clean: str, has_actionable_state: bool) -> bool:
    # 1. 否定词：不要撤销 / 先别丢弃 / 不能采用 → False（不直达）
    if _contains_any(clean, ("不要", "先别", "不能", "不该", "别", "别急", "不是")):
        return False
    # 2. 疑问/讨论语气：该不该定稿 / 为什么不能采用 / 讨论一下 → False
    if _contains_any(clean, ("该不该", "为什么", "讨论", "怎么样", "？", "?")):
        return False
    # 3. 状态校验：当前无可撤销/可采用对象 → False（交给 LLM 或明确提示）
    if not has_actionable_state:
        return False
    # 4. 明确动作目标（撤销/采用/丢弃/定稿 单独成句或带对象）
    return True
```

补充：
- `has_actionable_state` 升级为动作集合 `available_actions: set[str]`（`{"accept","discard","revert"}`），
  由调用方注入：查 `change_sets` / `generation_records` 分别得出各动作可用性（"有可回滚对象"≠"有可采用候选稿"）
- **规则降级路径同步支持否定/疑问**：`classify_rule` 先做否定/疑问检测（见补锁 5），无 Key 时"不要撤销，继续修改"仍识别为 rewrite
- **分类结果本身永不修改数据**——正式操作仍走 confirm / accept / discard / revert 接口

### 决策 5：LLM 输出使用严格结构化模型（Pydantic）

```python
class StrictModel(BaseModel):
    # 严格模式：额外字段直接校验失败（LLM 多输出 requires_confirmation 等 → 拒绝 → 规则回退）
    model_config = ConfigDict(extra="forbid", strict=True)

class Operation(str, Enum):
    STRENGTHEN_CHARACTER_PORTRAYAL = "strengthen_character_portrayal"
    REWRITE_CHAPTER = "rewrite_chapter"
    COMPRESS_CHAPTER = "compress_chapter"
    # ... 白名单枚举，拒绝任意字符串

class Dependency(StrictModel):
    from_step: int   # 1-based
    to_step: int     # 1-based；from_step != to_step
    kind: Literal["depends_on"] = "depends_on"

class IntentStep(StrictModel):
    intent: Literal["knowledge_query", "discussion", "rewrite", "data_operation", "flow_control"]
    raw: str = Field(max_length=200)
    target_chapter_no: int | None = Field(default=None, ge=1)

class IntentPlan(StrictModel):
    """内部模型：仅供 LLM 解析与校验，不直接出网。"""
    steps: list[IntentStep] = Field(default_factory=list)
    dependencies: list[Dependency] = Field(default_factory=list)
    # 结构校验（model_validator）：
    #   - 依赖的 from_step / to_step 必须指向存在的步骤（1..len(steps)）
    #   - from_step != to_step
    #   - 依赖图必须无环（DFS 拓扑校验）——违反一律视为 LLM 输出非法 → 规则回退

class LLMIntentOutput(StrictModel):
    intent: Literal["knowledge_query", "discussion", "rewrite", "data_operation", "flow_control"]
    operation: Operation | None = None    # 白名单枚举
    target_scope: Literal["current_chapter", "explicit_chapter", "project_level", "none"] = "none"
    target_chapter_no: int | None = Field(default=None, ge=1)
    mentioned_entities: list[str] = Field(default_factory=list, max_length=20)
    requirements: list[str] = Field(default_factory=list, max_length=10)
    needs_clarification: bool = False     # 仅建议，最终以后端目标校验为准
    clarification_question: str | None = Field(default=None, max_length=200)
    plan: IntentPlan | None = None        # 复合任务完整计划（单一权威）；单步为 None
    # 无 requires_confirmation 字段——后端按 intent + operation + risk_level 计算

def to_conversation_plan(llm_plan: IntentPlan) -> dict:
    """内部 IntentPlan → 对外 ConversationPlan（兼容现有前端契约）。

    现有前端契约（frontend/src/api/chat.ts）：
      {plan_id, steps: [{intent, target?, query?, based_on?}],
       dependencies: [{step: number, depends_on: number[]}]}
    """
    # 前端契约：target?: string | Record<string, unknown> | null ——
    # 传 int 不兼容，统一转对象 {"chapter_no": N}（便于后续扩展）
    return {
        "plan_id": uuid4().hex,
        "steps": [
            {"intent": s.intent,
             "target": {"chapter_no": s.target_chapter_no} if s.target_chapter_no is not None else None,
             "query": s.raw if s.intent == "knowledge_query" else None,
             "based_on": None}
            for s in llm_plan.steps
        ],
        # 依赖按 to_step 聚合：同一目标步骤的多个前置合并为一个依赖项
        "dependencies": [
            {"step": to_step, "depends_on": sorted({d.from_step for d in deps})}
            for to_step, deps in itertools.groupby(
                sorted(llm_plan.dependencies, key=lambda d: d.to_step),
                key=lambda d: d.to_step)
        ],
    }
```

**两层结构明确**：
- `LLMIntentOutput.plan: IntentPlan`——内部模型，严格校验用，不出网
- `ConversationPlan`——对外 API 结构，由 `to_conversation_plan()` 转换，兼容现有前端
- **前端零改动**（现有 `ConversationPlan` 类型不变）；`plan_id` 由转换层生成
- **target 类型对齐**：`ConversationPlanStep.target` 前端为 `string | Record<string, unknown> | null`，
  转换统一输出 `{"chapter_no": N}` 对象（不传裸 int）
- **依赖聚合**：多前置依赖合并为单条 `{step, depends_on: [1,3]}`（按 to_step 分组），不再逐条重复


- 用 `model_validate_json` 严格解析，**废除"从任意文本搜索 intent 字符串"的宽松解析**
- `requires_confirmation` / `needs_clarification` 仅作建议，后端按风险等级与目标校验计算（补锁 1）
- 结构校验：依赖下标必须指向存在的 step；复合任务含不支持步骤 → `intent_unsupported`（补锁 4）
- `data_operation`（改人物档案/设定）与 `rewrite`（改章节正文里的表现）严格区分：`mentioned_entities` 不触发人物档案修改
- 解析失败 / 校验失败 → 规则回退（`llm_used=False` 标记）

### 决策 6：任务卡 + 人工确认仍是最终安全边界

- 章节存在性校验只是"目标可解析"，**不保证选对章节**
- 真正的安全闭环：任务卡明确展示目标章节 → 用户确认 → 生成候选稿 → 人工采用/丢弃
- 方案文档与实现注释必须明确这一点，不把"存在性校验"描述成安全保证

## 4. 安全与降级矩阵

| 场景 | 行为 |
|------|------|
| Key 就绪 + LLM 正常 | LLM 理解（意图+目标+步骤），规则护栏校验 |
| Key 就绪 + LLM 非法 JSON / 结构不过 | 规则回退（现有逻辑，`llm_used=False`） |
| 无 Key / provider 不可用 | 规则回退（不发幻觉、不显示假成功） |
| 流程控制预筛通过 | 规则直达（不依赖 LLM） |
| LLM 目标章节不存在 | 澄清（不偷偷回退当前章节） |
| 用户显式写章节 ≠ LLM 推断 | 用户显式优先 |
| 复合任务 | LLM 输出完整 steps（单一权威）；LLM 不可用时规则拆步降级 |
| 提示词注入（要求输出非白名单意图） | Pydantic Literal 拒绝 → 规则回退 |

## 6. 风险与边界（第一版明确限制）

1. **knowledge_query 暂不接 RAG**：分类变准后仍回复"请到资料问答入口查询"——第一版限制，方案里明确，不做假执行
2. **data_operation 暂不执行**：LLM 能识别"改人物档案"，但第一版无执行能力 → `intent_unsupported` 明确提示
3. **延迟**：每次消息多一次 LLM 调用（~1-3s）。V2 可做"规则先回 + LLM 后修正"流式；当前幂等键缓存首次响应可复用
4. **成本**：意图抽取 max_tokens≈300，可控；可加同内容短时缓存
